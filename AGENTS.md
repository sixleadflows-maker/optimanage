# OptiManage — Project Context

This is a **real, live production system** for EyeSpy (formerly Noor Optics — rebranded July 2026), an optical retail shop in Karachi, Pakistan — inventory, POS, prescriptions, lab orders, suppliers, customer CRM, analytics, and (since July 2026) a public customer-facing storefront with online checkout. `README.md` is stale and still describes an old mock-data prototype version of this app — ignore it for current state; this file is the source of truth. Check `git log` for detailed feature history rather than expecting it enumerated here.

## Stack
- Next.js 16 App Router + Turbopack, TypeScript, Tailwind CSS v4
- Prisma 7 with `@prisma/adapter-neon` (NOT plain `new PrismaClient()`) → Neon Postgres, database `optimanage`
- NextAuth v5, credentials + bcrypt, for staff login. The `jwt` callback in `src/lib/auth.ts` re-reads the account (cached 30s per instance) so role/name/location edits and deactivation apply without the person signing out. That callback must never throw — Auth.js clears the session cookie on any error, signing the user out.
- Vercel deployment, no VPS, no separate staging environment

## Deployment topology — two Vercel projects, one repo, one database
- **optimanage** project → https://optimanage-nu.vercel.app — the staff dashboard/POS, used daily at the outlet. `/` redirects to `/login`.
- **noor-optics-shop** project → https://noor-optics-shop.vercel.app — the public customer storefront. Same codebase and same GitHub repo (`sixleadflows-maker/optimanage`, `master` branch) — one push deploys both.
- `src/middleware.ts` makes the *same* deployed code behave differently per domain: it rewrites `/` → `/shop` only when the request's Host header matches something in the `STOREFRONT_HOSTNAMES` env var (comma-separated, substring-matched). That var is set only on the `noor-optics-shop` project.
- Both projects need their own `DATABASE_URL` and `AUTH_SECRET` set in Vercel project settings. Vercel marks these "Sensitive" — **write-only forever**, there is no reveal/copy button once saved, not even for whoever set it. If you need the DB connection string again, get it fresh from the Neon console, not from the other Vercel project's settings.
- A brand-new Vercel project created via `vercel project add` defaults to Framework Preset **"Other"**, not Next.js, even after a successful `next build` deploy — this causes a platform-level 404 (`X-Vercel-Error: NOT_FOUND`, request never reaches the app) despite a green build. Fix once with `vercel project update <name> --framework nextjs`, then redeploy.

## Codebase conventions
- Pages follow: Server Component `page.tsx` fetches data via functions in `src/lib/data.ts`, passes it to a sibling `*Client.tsx` (`"use client"`) that handles interactivity/state.
- Mutations live in `src/lib/actions/*.ts` (`"use server"` files). Every export in one of these files must be an async function:
  - A plain constant export (e.g. `export const FOO = [...]`) crashes the page the moment it's touched.
  - `export type { Foo }` (re-exporting a type) silently breaks the Server Actions bundle with a `ReferenceError` — not caught by `tsc`, only surfaces as a real 500 the first time that specific action is invoked. Keep shared types in a plain non-`"use server"` module instead and import them from there.
- Expected failures in a Server Action (out of stock, invalid input, not allowed) must be **returned** as `{ ok: false, error }`, not thrown. In production Next.js replaces a thrown error's message with a generic one, so staff never see the reason — this is how invoice deletion "silently failed" and how an out-of-stock sale got mistaken for "offline" at the till. Reserve `throw` for genuine crashes.
- `revalidatePath()` only works from a genuine Server Action or Route Handler — never from code a Server Component's render reaches directly, even one `await` removed. If a mutation needs to happen as part of a page rendering (e.g. a payment-confirmation page finishing up an order), wrap it in its own dedicated Server Action and trigger that from a small client component, not from the page itself.
- Search boxes on list pages filter with `matchesSearch` (`src/lib/utils/search.ts`): every word typed must appear somewhere across the record's fields, punctuation ignored ("rayban aviator" finds brand "Ray-Ban" + name "Aviator"). Don't hand-roll `a.includes(q) || b.includes(q)` again — that fails as soon as someone types brand and name together. Give a search box its own row; sharing one with a long row of filter buttons squeezed the Products search down to a stub.
- A page left open across a release keeps running old code, and the server can stop recognising its Server Actions (the action IDs change whenever Next's encryption key rotates, every ~14 days): every search and save from that page then fails until it's refreshed. `UpdateNotice` (dashboard layout) compares the build's `NEXT_PUBLIC_BUILD_VERSION` with `/api/version` and asks staff to refresh — it never reloads by itself, the till may have a bill in progress. Where a failed action is caught, check `unstable_isUnrecognizedActionError(e)` and call `reportOutdatedPage()` rather than blaming the connection.
- Design system: glass-morphism (`.glass-card`, `.glass-modal`, `.glass-input` in `globals.css`), primary `#6d5ef0`, secondary `#14b8a6`, Manrope for display/headings. The old blue `#1f5d8c` was deliberately purged — don't reintroduce it.
- Prisma client generates to `src/generated/prisma` (gitignored). After any `schema.prisma` change: `npm run db:push` then `npx prisma generate`.

## Key areas
- Sale creation core: `src/lib/sales/core.ts` (`persistSale`) — shared by POS (`src/lib/actions/sales.ts`) and online orders (`src/lib/orders/fulfillOnlineOrder.ts`) so there's exactly one implementation of totals math and stock deduction. Stock is decremented via an atomic conditional `updateMany({ where: { stock: { gte: qty } } })` per item, not a naive read-then-write, specifically to prevent overselling under concurrent sales. `reviseSale` (editing a finished invoice) and `recordSalePayment` (settling an advance later) live in the same module and share `priceSale`, so a corrected bill can never be worked out differently from a fresh one. Editing moves stock by the **difference** only. Lines are matched by id and changed **in place**, never deleted and re-created, because a `ReturnItem` points at its `SaleItem`: a line with units returned must stay, as the same item, with at least that many — so invoices with a return can be edited. The amount taken at the till is part of the edit (`payment.atTill`, or the split parts), so lowering a fully paid invoice works; it's refused only when the new paid amount would exceed the new total. `attachCustomerToSale` puts a walk-in invoice on a customer later (spend and visits follow the invoice), which is what adding a prescription to a walk-in invoice does. Sale lines with `productId: null` are items typed in at the till (no stock).
- Deleting is never destructive. Rows that other records point at (products, customers, suppliers, labs, staff, locations) are hidden with `active:false` + `deletedAt` and un-hidden on restore; "delete permanently" sets `deletedAt` to `TRASH_PURGED_AT` (the epoch) so it drops out of the trash and can't be restored, while past invoices keep showing the name — those rows are never really deleted. A hidden staff row would otherwise keep holding its unique sign-in email forever, so look that up through `userHoldingEmail` in `src/lib/trash/heldValues.ts`, which frees it from a row that's gone for good. **Customer phone numbers are not unique** (owner's rule, Sept 2026): one contact number can carry several customers — a family on one phone, or a separate record per order — so adding or editing a customer never fails on the number. The forms show who's already on it (`samePhone`/`phoneKey` in `src/lib/utils/phone.ts`, which treat `+92 300…`, `0300-…` and `0300…` as one number) and let staff pick one instead; never reintroduce `findUnique({ where: { phone } })` or an "already exists" refusal. A bill recorded without asking anyone matches on number **and** name (`customersWithPhone` + `sameName`). Records that ARE removed (invoices, returns, expenses, prescriptions, lab orders, purchase orders, stock changes, payments taken on an invoice) are copied into `TrashEntry` first by `src/lib/trash/snapshots.ts`, which also reverses their effects and re-applies them on restore. That snapshot approach is deliberate: soft-deleting invoices would mean adding a `deletedAt` filter to ~20 sale queries, and one missed filter puts a deleted invoice back into revenue.
- Cash the owner takes to the bank is a `BankDeposit`, **not** an `Expense`: it leaves the drawer (so `getCashCollection`, `openingCashFor` and the day close subtract it from the expected cash) but it's not a cost, so it must never reach profit or Analytics. Only cash expenses (`paymentMethod === "Cash"`) come off the drawer; card and cheque expenses are listed apart. Deposits are trashed by snapshot like expenses.
- Any document number (INV/RET/LAB/PO) comes from `nextDocumentNumber`'s stored counter, which only moves forward — never from a count or max of existing rows. Deletion and restore both depend on it: a number in the trash must not be handed to a new record, or the restore collides. `nextDocumentNumber` takes the year, so an invoice entered for a past date is numbered in that year's series.
- A bill made while the till is offline is printed immediately with a temporary `offlineRef` (`OFF-MMDD-XXXX`), queued in localStorage, and synced by itself. Every till sale carries a `clientRef`, so a sale whose reply was lost is never recorded twice — `persistSale` returns the existing invoice instead. Offline sales sync with `allowOversell` (the goods already left the shop, so the sale is recorded even if the count says otherwise, and the affected items are reported) and with the time they were rung up, so they land on the right day in Cash Collection.
- Money taken after the sale goes in `SalePayment`, never by just bumping `Sale.paid` on its own: the day's cash collection (`getCashCollection`) credits each payment to the day it was taken, so a March advance settled in April shows in April's drawer. `Sale.paid` stays the running total, so `getCashCollection` subtracts a sale's `SalePayment` rows from it to recover what was taken at the till that day. Status and balance always come from `settleInvoice` (`src/lib/sales/settle.ts`): paid in full → PAID, nothing paid → BALANCE, part paid keeps its label (a "Balance" customer who pays Rs.1,500 of Rs.1,800 stays on Balance with Rs.300 owed), otherwise ADVANCE. At the till, Balance can take a part payment too — it travels as `balancePaid`, never `advanceAmount`, because older tills still send a leftover advance figure with Balance bills. `Customer.totalSpend` tracks invoice **totals**, not payments — a later payment must not touch it, an edit moves it by the difference. Invoice/return numbers come from the `DocumentCounter` table (`nextDocumentNumber`), never from counting rows — invoices can be deleted, and a count would reuse or collide with an existing number.
- A customer can pay money ahead for the shop to hold ("advance held", the `CustomerCredit` table: a row above zero when it's paid in, below zero when some is handed back). What they've **spent** from it is never stored there: it is the `SalePayment` rows with method `CREDIT_METHOD` ("From advance") on their invoices, and what's held is always worked out by `creditHeld` / `creditHeldByCustomer` in `src/lib/sales/credit.ts` — so editing, deleting or restoring an invoice or payment keeps it right with no syncing. Never add a running-total column. The advance is cash in the drawer on the day it's paid in (and out on the day it's refunded); a payment "From advance" brings nothing in that day, so `getCashCollection`/`openingCashFor` count `CustomerCredit` rows and skip `CREDIT_METHOD` payments. It's not revenue until an invoice uses it. `CREDIT_METHOD` is not one of `PAYMENT_METHODS` and must never be stored as money taken at the till.
- Split payments (part cash, part card…): `Sale.paymentSplit` (JSON, `[]` when one method) holds the parts of the amount taken **at the till**, and `paymentMethod` then holds a display label like `"Cash + Card"` — never a real method, so anything that needs a method must go through `src/lib/sales/paymentSplit.ts` (`tillParts` for cash reports, `primaryMethod` for defaults). Invariant: the parts sum to `paid` minus the sale's `SalePayment` rows; `persistSale`/`reviseSale` refuse a split that doesn't, and any code path that changes the at-till amount must rewrite the split too.
- Storefront: `src/app/shop/**` (public routes, no auth). Checkout flow: `src/lib/actions/storefront.ts` (`initiateCheckout`) → `CheckoutSession` row → payment gateway → `src/lib/orders/fulfillOnlineOrder.ts` converts a paid session into a real `Sale` with `source: ONLINE`.
- Payments: `src/lib/payments/swich.ts`. Swich is the chosen gateway (Pakistan-first aggregator: cards, JazzCash, EasyPaisa, bank via 1LINK). Their docs site is JS-rendered and wasn't scrapable when this was built, so the module runs in **mock mode** whenever `SWICH_API_KEY` is unset — it simulates instant payment success so the whole storefront flow is testable without real credentials. Do not invent real Swich endpoint paths or field names; get them from the owner's actual merchant dashboard once they have one, and wire the real HTTP calls in behind the existing function signatures.
- Print output: `.receipt-paper` (80mm thermal) and `.a4-invoice` classes in `globals.css`, rendered in `POSClient.tsx`. A print-scoped rule forces `font-weight: 700 !important` on both, because thin strokes (Courier New, default-weight body text) print faint on thermal printers — the on-screen previews intentionally stay at normal weight, only the physical printout is bold.

## Staff login credentials
Do not hardcode these in any file that gets committed. Dev/seed logins are defined in `prisma/seed.ts` (one OWNER, one MANAGER, two CASHIER accounts) — read that file directly if you need to log in locally. The live production DB uses the same accounts (there's no separate staging DB), so treat them as real credentials, not throwaway demo values. The user emails deliberately still end in `@nooroptics.pk` after the EyeSpy rebrand — they're live usernames staff type at login, so renaming them requires a coordinated credential rotation, not a find-and-replace (the login page placeholder matches them on purpose).

## Local development
`npm run dev` (Turbopack). Needs `DATABASE_URL` + `AUTH_SECRET` in `.env`/`.env.local` pointing at the **same live Neon database used in production** — there is no separate dev/staging DB. Always clean up any test sales/customers/stock changes with a throwaway `tsx` script immediately after verifying a feature; don't leave test data in the shared production DB.
